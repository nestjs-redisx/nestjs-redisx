# Changelog

All notable changes to NestJS RedisX are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [1.14.0] - 2026-10-09

### Added

- **New package `@nestjs-redisx/semaphore`** — distributed counting semaphore: at most N concurrent executions fleet-wide (roadmap #50).
  - **Permit leases** over one sorted set per semaphore (member = permit id, score = expiry): acquire sweeps expired permits and grants a seat only under capacity, all inside a single atomic Lua script — a crashed holder frees its seat after the TTL with no background job. The semaphore key carries a `PEXPIRE` at least as long as its longest permit, so abandoned semaphores leave no residue. Single-key and cluster-safe without hash tags; no ZADD flags, so the scripts run byte-for-byte on the in-memory testing driver.
  - **`SEMAPHORE_SERVICE` (`ISemaphoreService`)**: `acquire` (exponential backoff bounded by `waitTimeout`), `tryAcquire`, `withPermit`, `usedPermits`, `availablePermits`, `forceReleaseAll`. Auto-renewal keeps long-running work seated and stops the moment a permit is lost; graceful shutdown releases every held permit so waiters take over immediately instead of after the TTL. `permit.release()` throws `SemaphorePermitNotHeldError` when the seat expired before the work finished — the honest report that the bound was not held.
  - **`@WithSemaphore` decorator** — proxy-based, works on any `@Injectable` method: `{n}` key templates or a key builder, `onUnavailable` policy (`throw` | `skip` | custom error, applied to acquisition only), fail-open without the plugin (a missing ceiling is observable; a silently skipped business method is not), and metadata carry-over so `@Cron` below it stays registered.
  - Fail-fast validation on the sync and `registerAsync` paths AND in the service constructor; NOSCRIPT falls back to `EVAL`; Lua pre-load failures degrade to lazy loading instead of crashing bootstrap. With `MetricsPlugin`: `redisx_semaphore_acquisitions_total{status}`, `redisx_semaphore_wait_duration_seconds`, `redisx_semaphore_hold_duration_seconds`, `redisx_semaphore_permits_active`; with `TracingPlugin`: a `semaphore.acquire` span per acquisition.
- **New package `@nestjs-redisx/dedup`** — event deduplication and distributed debounce: run webhooks, queue messages, and user actions once per window across the fleet (roadmap #17).
  - **First-wins markers** (`SET NX PX` with an owner token): exactly one winner per key per window across every instance. A FAILED first execution releases its own marker via CAS Lua — a newer marker is never erased — so retries are not locked out for the rest of the window; a crash leaves the marker until the TTL.
  - **Distributed trailing debounce**: every call stamps itself as the LAST caller; after the quiet window the still-last caller claims the slot atomically and executes — superseded calls resolve `undefined`. The pending timer is in-process and unref'd (best-effort, like a local debounce — documented).
  - **`DEDUP_SERVICE` (`IDedupService`)**: `isFirst` / `dedupe` / `debounce` / `release`. Gates (`dedupe`, `debounce`, `@Dedupe`) honor `errorPolicy` `'fail-open'` (default: run without deduplication, loudly) | `'fail-closed'` (throw `DedupStoreError`); manual APIs are always strict. `redisx_dedup_checks_total{outcome}` with `MetricsPlugin`.
  - **`@Dedupe` decorator** with `{n}` key templates, fail-open without the plugin, and metadata carry-over. The boundary vs idempotency is documented: dedup is a lightweight marker — request-grade response replay stays in `@nestjs-redisx/idempotency`.
- **New package `@nestjs-redisx/counters`** — atomic counters and sequences: fleet-wide counters that never lose updates (roadmap #18).
  - **`COUNTER_SERVICE` (`ICounterService`)**: `increment`/`decrement` (validated non-zero safe integers, negatives allowed), `get` (0 when absent, loud `CounterValueError` on a non-numeric key instead of silent `NaN`), `set`, `reset`, `getAndReset` (atomic read-and-zero for batch flushes), `next`/`current` (monotonic fleet-wide sequences, never a TTL).
  - **Window counters**: `increment(key, by, { ttl })` applies the TTL only when the mutation CREATES the key (atomic Lua: `EXISTS` check before `INCRBY`, `PEXPIRE` only on creation — a pre-existing permanent counter is never retrofitted with a window) — daily/hourly keys expire on their own and later increments never extend the window. Plain `INCRBY` on the unwindowed path.
- **Fixed: proxy decorators above `@Cron` silently unregistered the job.** `@WithLock`, `@WithCircuitBreaker`, `@Cached`, `@InvalidateTags`, and `@InvalidateOn` replace the method descriptor with a wrapper but did not copy the metadata that decorators below them had stamped on the ORIGINAL method — so writing any of them above `@Cron()` removed the cron job on every instance with zero signal (the scheduler discovers jobs by reading metadata off the prototype's method, which is the wrapper). The same defect class was fixed for `@LeaderOnly` in 1.13.0; all five wrappers now carry over every stamped metadata key before adding their own options, each covered by a regression test. `@Idempotent`, `@Cacheable`/`@CachePut`/`@CacheEvict`, and the guard/discovery decorators never wrapped the descriptor and were unaffected.
- All three new plugins ship the full pipeline: dual CJS + ESM build, `globalThis` decorator registries (dual-package safe), reference docs with compiled snippets, llms catalog coverage, sections in the canonical plugins-on-memory suite, memory + live-Redis integration tests, and ≥95% branch coverage.
- **Adversarial-hardening pass over everything above** (four independent review lenses — concurrency/lifecycle, Lua/Redis semantics, failure containment, docs-vs-code — plus the author's own attack round; every fix landed test-first):
  - `semaphore`: **shutdown no longer yanks seats from under still-running work** — releasing every permit in `onModuleDestroy` let another instance start the same bounded work while this instance's handler was still executing (a silent split bound, with the loud not-held signal suppressed as a bonus); shutdown now stops auto-renewal and lets seats lapse within their remaining TTL (the documented crash bound), while an owner's own release still lands instantly. A `destroyed` flag aborts an acquire sleeping in backoff (reason `'shutdown'`) and quietly gives back a seat won on the wire mid-shutdown — previously that permit auto-renewed forever on a still-alive process.
  - `semaphore`: **all expiry decisions moved to the Redis server clock** (cached `TIME` offset, 30s re-sync) — the acquire sweep trusted each caller's local clock, so one instance skewed forward by more than `ttl − age(freshest renewal)` swept every OTHER instance's live permits and over-admitted.
  - `semaphore`: `release()` is **expiry-aware** (a bare `ZREM` reported "was held" for an expired-but-unswept seat, hiding exactly the violation the loud release exists to surface) and **single-flight** (two concurrent releases double-ZREM'd and the loser threw a false `SemaphorePermitNotHeldError`); `forceReleaseAll` reports LIVE holders only; `usedPermits` is a read-only `ZCOUNT` (the write-sweep variant failed under `maxmemory`); auto-renewal **retries through transient store errors** while the lease is alive instead of dying permanently on the first blip (the OOM-aborted re-score included), stopping only on a confirmed loss or lapse.
  - `semaphore`: store outages during acquisition are wrapped as `SemaphoreAcquisitionError('error', cause)` and the reasons are now real (`'exhausted'` retry cap vs `'timeout'` wait budget vs `'error'` vs `'shutdown'`); `@WithSemaphore`'s `onUnavailable` detects failures **cross-copy-safely by error code** (a mixed CJS+ESM process kept the policy dead via `instanceof`), a policy function returning a non-Error falls back to the original error instead of `throw undefined`, and per-call `ttl`/`waitTimeout`/`retry` overrides are validated fail-fast (a negative ttl minted an already-expired permit; `maxRetries: Infinity` looped forever).
  - `semaphore` + `dedup`: **every user-extensible observability emit is contained** (metrics, tracing spans, `startSpan` itself) — a throwing metrics implementation after the store granted a seat leaked it unreleasable until TTL, and after `markFirst` it burned the dedup window with the event marked but never handled; containment paths are TOTAL (nullish rejections, `throw undefined`, throwing log lines).
  - `dedup`: the debounce **claim step never runs-anyway** — under `fail-open` a store blip at claim time executed a possibly-superseded round on top of the real winner's execution; it now skips loudly (fail-closed still throws). A **stamp** failure under fail-open waits the quiet window before running instead of executing with zero delay. The claim distinguishes **expired slots from supersession** (`-1`/`0`/`1`), so a round lost to a stalled process (suspend/SIGSTOP past the 5s grace — grace raised from 1s) is logged as LOST instead of silently swallowed. The debounce slot moved to a **NUL-delimited internal namespace** (user keys reject `U+0000`), so `dedupe('debounce:x')` can no longer collide with `debounce('x')` and have its marker destroyed by a plain-SET stamp.
  - `counters`: the window TTL is **EXISTS-gated** (`PTTL < 0` retrofitted a window onto pre-existing permanent counters — contradicting the documented first-write semantics); `set()` without a ttl **preserves an existing window** via a PTTL-carrying Lua (a plain SET made a corrected daily counter permanent, silently double-counting from the next day on); `getAndReset` **preserves evidence** (a clearly-non-numeric value is reported without deleting the key); reads reject blank/garbage/float strings AND integers past 2⁵³ with `CounterValueError` carrying the ACTUAL raw value (blank strings parsed as a legitimate 0; 2⁵³⁺ precision loss would mint duplicate sequence ids).
  - `testing`: the in-memory Lua interpreter's `tonumber` now matches real Lua on blank strings (`tonumber('')` is nil, not 0 — guards behaved differently on the memory driver than on Redis), and the executor gained `TIME`.
  - Template-key footgun made loud: `@WithSemaphore`/`@Dedupe` warn once per site when a `{n}` placeholder interpolates an object as `[object Object]` (every call collapsing onto ONE key: a global semaphore / distinct events skipped as duplicates); the dedup troubleshooting page's misdiagnosis of this case is rewritten; four doc locations promising a "no-op release" after `forceReleaseAll` now state the real taken-away signal.

## [1.13.0] - 2026-09-09

### Added

- **New package `@nestjs-redisx/leader`** — leader election for multi-instance deployments: run cron jobs, migrations, and cleanup on exactly one instance. Closes roadmap #51/#19.
  - **`@LeaderOnly()` decorator** — proxy-based, works on any regular `@Injectable` method (generators are rejected at class load — see the hardening notes below) and composes with `@nestjs/schedule`: `@Cron` fires on every instance, the body runs only where the lease is held. Groups referenced by decorators register at decoration time and their elections start at bootstrap; the first election round is awaited during `onModuleInit`, so leadership is resolved before the first cron tick. Fail-safe skip: without the plugin the method runs NOWHERE (with a one-time warning) — for singleton work "nobody runs" is recoverable, "everybody runs" is not.
  - **Lease-based election per group** over a single Redis key: `SET NX PX` acquire, CAS Lua heartbeat renewal, CAS release — single-key and cluster-safe without hash tags, and fully supported by the in-memory testing driver.
  - **Fail-safe local view**: `isLeader()` is true only while the last CONFIRMED lease is unexpired. A rejected or errored renewal demotes immediately, a stalled event loop cannot sustain a stale claim, and Redis being down means nobody leads (work pauses rather than duplicates). Background store errors never crash the app.
  - **Failover**: instant on graceful shutdown and `stepDown()` (lease released; takeover within `retryIntervalMs`), bounded by `ttlMs + retryIntervalMs` after a crash. `stepDown()` adds a one-`ttlMs` candidacy cooldown so another instance wins the freed seat.
  - **`LEADER_SERVICE` (`ILeaderService`)**: `instanceId`, `isLeader`, `getLeaderId`, `runIfLeader`, `stepDown`, `getGroups`; `onElected`/`onLost(reason)` lifecycle callbacks (fire-and-forget) and, with `MetricsPlugin`, `redisx_leader_elected_total`/`redisx_leader_lost_total` counters.
  - Fail-fast validation (`InvalidLeaderConfigError`, new core codes `LEADER_CONFIG_INVALID`/`LEADER_STORE_ERROR`): positive safe-integer timings, `renewIntervalMs` strictly below `ttlMs`, sane group names — on both sync and `registerAsync` paths.
- `core`: **plugin cleanups can now talk to Redis during shutdown.** `RedisService` and `RedisClientManager` close clients in `onApplicationShutdown` (phase 3) instead of `onModuleDestroy` (phase 1). Nest runs a module's phase hooks concurrently, so closing the connections in phase 1 raced — and routinely beat — every plugin cleanup that needs Redis on shutdown — the leader lease release (found by the live failover test: the lease survived a graceful stop and failover degraded from instant to TTL-bound), lock releases, and stream consumer teardown. Clients still close on application shutdown, just after dependents clean up.
- `leader`: **adversarial-hardening pass** (three independent pre-release review rounds; every fix landed test-first):
  - in-flight tick races: a store call already on the wire when `stepDown()`/shutdown superseded the election could resurrect or grant leadership when it landed — a pending renewal re-promoted a stepped-down instance after its key was released (split-brain `@LeaderOnly` execution for up to a heartbeat, plus a duplicate `onLost`), a pending acquire resolving after destroy left the lease held by a dead process (failover blocked for a full `ttlMs`), and a follower's raced acquire survived its own cooldown. Elections now carry an epoch bumped on supersession; stale results are discarded and any lease they still won or extended on the wire is best-effort released;
  - a throwing user-supplied metrics implementation could permanently kill an election loop (the counter emit ran before the reschedule); counter increments are now contained like callbacks;
  - NOSCRIPT-fallback failures in the store adapter are wrapped in `LeaderStoreError` like every other store error;
  - `keyPrefix` is validated (non-empty string — an empty prefix made the election key a bare group name);
  - **self-lockout on a still-held own lease**: acquire was a plain `SET NX`, so an instance could never re-take a key that still carried its OWN id. After a single transient renewal error the fail-safe demotion left the key behind and `SET NX` lost to it — a guaranteed leaderless window of up to the remaining `ttlMs` after every Redis blip, even in a single-instance deployment; an unclean restart with a stable `instanceId` (the documented pod-name setup) likewise waited out its own stale lease. Acquire is now an atomic acquire-or-re-claim Lua script (`SET NX PX`, else same-holder `PEXPIRE`): a transient renewal error costs one `retryIntervalMs` of leadership, a restarted leader re-leads at boot, and a seat held by another instance still can never be touched (verified against live Redis, the in-memory Lua interpreter, and a two-instance adversarial timeline asserting the at-most-one-leader invariant);
  - **silent forever-skip of late-registered groups**: elections start once, from the groups known at `onModuleInit`; a `@LeaderOnly({ group })` class loaded lazily after bootstrap registered a group nobody elects, so the method skipped on every instance with zero signal. `isLeader` now warns once per group when consulted about a group with no running election (suppressed before initialization);
  - `LeaderService` validates options in its constructor — the service is exported for direct wiring, and the plugin-only validation let a hand-constructed `renewIntervalMs >= ttlMs` service flap on every heartbeat; the plugin also defensively copies the `groups` array so post-registration mutation cannot change which elections start;
  - **shutdown/stepDown residue**: graceful shutdown and `stepDown()` released the lease only when the instance was locally the leader — but a fail-safe demotion (renewal store error) demotes locally while the key can still carry this instance's id, so a graceful stop in that state left a dead process's lease blocking the group for the remaining `ttlMs`, silently degrading the promised instant failover to TTL-bound. The election state now tracks whether the store may still hold our id (set on every confirmed acquire/renewal, cleared only when the store confirms the seat is not ours), and shutdown/stepDown release the key whenever it might be held — CAS on the own id, so a seat somebody else took is never touched, and a confirmed non-holder still costs no extra round-trip;
  - **event pairing across passive lease lapse**: a lease that expired without any tick observing it (event-loop stall, clock jump, store latency beyond `ttlMs - renewIntervalMs`) skipped its `onLost` — the next tick jumped straight to re-election and fired a second `onElected` with no loss in between, double-starting consumers that pair the callbacks to start/stop singleton workers (and under-counting `redisx_leader_lost_total`). The lapse is now reconciled at every tick/stepDown/shutdown entry: `onLost(group, 'expired')` fires before any re-election, keeping elected/lost strictly alternating per group;
  - **`@LeaderOnly` above `@Cron` silently unregistered the job**: decorators apply bottom-up, so in that order `@Cron` stamped its schedule metadata on the ORIGINAL method and the `@LeaderOnly` wrapper replaced it — the scheduler explorer, which reads metadata off the prototype's method, never saw the cron and the job ran NOWHERE with zero signal (the docs already promised both orders work). The wrapper now carries over all metadata stamped on the original method;
  - **stale-release/fresh-acquire wire race**: the best-effort release of a lease a superseded tick won on the wire was fire-and-forget; the store port guarantees no call ordering, so a delayed release could land AFTER this instance legitimately re-acquired post-cooldown and delete the fresh lease (same instance id, CAS passes) — local view says leader, key gone, split-brain until the next heartbeat. Pending stale releases are now tracked per election and candidacy waits for them to settle;
  - **`stepDown()`'s release could be overtaken by its own re-acquire**: the voluntary release was issued OUTSIDE that pending-release tracking, so one hanging on the wire for longer than the cooldown was overtaken by the post-cooldown re-acquire and landed last — deleting the legitimately re-acquired lease (same instance id, CAS passes) with the local view still saying leader: split-brain until the next heartbeat, through the exact hazard the tracking was built for. Every own-lease release (stale-sweep, `stepDown`, shutdown) now joins one per-election barrier that candidacy waits on, and `stepDown`/shutdown still await only their own release, so an older hung call cannot block them;
  - **untracked wire-won residue**: a lease that a superseded acquire or renewal won on the wire was only ever released best-effort — when that quiet release FAILED, nothing recorded that the store might still hold this instance's id, so a following `stepDown`/graceful shutdown skipped its safety release and the dead process's key blocked the group for the remaining `ttlMs` (the exact TTL-bound degradation the residue tracking exists to prevent). A stale wire-win now marks the may-hold flag (the wire result confirmed our id is on the key) and a settled quiet release clears it: a later `stepDown`/shutdown retries a failed release, and a confirmed one costs no redundant round-trip;
  - `@LeaderOnly` on a non-method member (getter, setter, property) now fails fast at class load with `InvalidLeaderConfigError` naming the member, instead of a cryptic `TypeError` — there is no method to gate, and a silent skip would run the body on every instance;
  - a destroyed `LeaderService` stays dead: `onModuleInit` landing after (or racing) `onModuleDestroy` — an aborted bootstrap, lifecycle misuse — could re-create election loops on a service whose teardown already ran; guarded by a terminal destroyed flag;
  - the `@LeaderOnly` service getter is now withdrawn on shutdown (identity-guarded, so a closing app never clobbers the getter a newer app registered — two Nest apps in one process): late cron ticks skip fail-safe instead of consulting a destroyed service.
- `core`: `PluginRegistryService` contains throwing third-party plugin `onModuleDestroy` hooks — an escaping throw aborted `app.close()` before `onApplicationShutdown` (leaking every Redis connection now that clients close in phase 3) and blocked the remaining plugins' cleanups.
- `leader`: **second adversarial-hardening pass** (four fresh independent review lenses against the already-hardened code; every fix landed test-first):
  - **shutdown rendezvous with the in-flight election round**: `onModuleDestroy` raced its own tick — a follower's acquire already on the wire when shutdown ran could WIN after destroy finished, leaving a dead process's lease blocking the group for a full `ttlMs` after a fully *graceful* stop (the compensating release was fire-and-forget and raced the closing Redis clients; a reply lost to the close never released at all), and with several groups a not-yet-stopped group could still elect — invoking the user's `onElected` — while destroy was busy releasing an earlier one. Shutdown now stops every loop synchronously first, rendezvouses (bounded by `retryIntervalMs`) with the round still on the wire, and awaits every pending release before returning, so wire-wins are observed and cleared while the clients are still open;
  - **lapse watchdog — the "stop the worker" event no longer waits for a hung socket**: the only emitter of an overdue `onLost` was the next tick, and the next tick is scheduled only after the current one's store call settles — with a black-holed connection and a driver without a command timeout (node-redis ships none), `isLeader()` correctly dropped at the deadline but the loss EVENT arrived only at TCP-retransmission timeout (minutes), so consumers pairing `onElected`/`onLost` to start/stop singleton workers ran two workers concurrently the whole time. A per-election watchdog now fires `onLost(group, 'expired')` at the lease deadline, supersedes the stuck round, and quietly releases anything it still won on the wire;
  - the store adapter's Lua pre-load no longer fails bootstrap: a transient hiccup exactly during init (`LOADING` after a Redis restart, a failover mid-deploy) crash-looped the whole application even though every runtime path degrades to plain `EVAL`; it now warns and continues;
  - the `LEADER_REDIS_DRIVER` factory rewrote EVERY `getClient` failure into "client not found" configuration advice — `ECONNREFUSED` during a deploy surfaced as instructions to edit the client list with the real cause discarded; only an actually-missing client maps to `InvalidLeaderConfigError` now, everything else propagates with its cause;
  - the `@LeaderOnly` service registry is a stack, not a single slot: with two Nest apps in one process, closing the NEWER app first wedged the survivor — its getter was gone and every decorated method skipped forever behind a misleading "is LeaderPlugin registered?" warning. The surviving app's service is re-exposed, and concurrent multi-app registration logs the arbitration rule (documented in troubleshooting);
  - generated instance ids carry 48 bits of randomness (up from 24): two replicas sharing an id BOTH win the election *by design* (acquire re-claims a key holding the caller's own id), so collisions must stay negligible even when hostname and pid coincide (pinned container hostnames, everything PID 1). The docs now say "unique per replica (e.g. the pod name)" instead of steering toward a shared host name, and state the real consequence of a shared id (election collapse, not just an ambiguous `getLeaderId()`); the monitoring page's "who leads now" PromQL — wrong for any leadership older than its window — was replaced with the status-endpoint guidance.
- `core`: **the node-redis driver applied `keyPrefix` to plain commands but not to EVAL/EVALSHA keys** — ioredis prefixes script keys natively, so under node-redis with a configured `keyPrefix` every Lua-scripted feature operated on UNPREFIXED keys while plain-command paths used prefixed ones: leader elections escaped their namespace (two apps isolated by prefix silently competed for one seat), `getLeaderId()` returned `null` forever while `@LeaderOnly` crons demonstrably ran, and a lock acquired via prefixed `SET NX` was "released" on a different key, so every lock survived to its full TTL. Script keys declared via `numkeys` are now prefixed exactly like ioredis does — the two drivers are key-compatible again.
- `metrics`: **a custom `prefix` silently disabled every feature-package metric** — plugins emit the canonical `redisx_*` names while the registry registered the series under the custom prefix, so lookups missed and no-oped with zero signal (the leader/locks/session counters documented as automatic never moved, and alerts built on them never fired). Canonical names now resolve against the configured prefix: a custom prefix renames the series instead of dropping them.
- `leader`: **third adversarial-hardening pass** (four more independent review lenses against the twice-hardened code):
  - **the lapse watchdog re-arms after a spurious wake**: timers run on the monotonic clock while the lease deadline is wall-clock, so a clock stepped BACKWARD between arming and the deadline made the watchdog wake "early", see an unlapsed lease, and silently disarm for the rest of the lease — removing it exactly in its target scenario (hung heartbeat), with the overdue `onLost('expired')` then delayed until the dead socket erred out. A spurious wake now re-arms for the remainder;
  - **shutdown awaits are bounded end-to-end**: the in-flight-tick rendezvous was bounded but the release awaits were not — on a black-holed connection `onModuleDestroy` waited forever for a release that could never land, wedging `app.close()` (and every later module's destroy hook) behind the leader plugin until the orchestrator SIGKILLed, and delaying `onLost('shutdown')` the same way. Every shutdown await now forfeits after one `retryIntervalMs` (the lease then expires by ttl — the crash bound), with the bound timer cancelled either way;
  - **configured durations are capped at 2³¹−1 ms (~24.8 days)** — Node's `setTimeout` clamps larger delays to 1 ms, so a `renewIntervalMs`/`retryIntervalMs` beyond the JS timer range (previously accepted up to 10 years) turned the configured cadence into a ~1 ms hot loop hammering Redis, and a `ttlMs` beyond it silently disarmed the lapse watchdog. `MAX_LEADER_TTL_MS` is now the timer cap and validation rejects anything above it.
- `core`: **the node-redis driver now honors `commandTimeout`** — the option is documented in `ConnectionConfig` (and defaulted to 5s by the ioredis adapter) but the node-redis adapter silently ignored it, leaving every command unbounded on a black-holed connection (renewals hanging for the TCP retransmission window, shutdown releases never settling). Opt-in, no default: when set, the adapter races each command against the deadline (the command may still execute server-side); long blocking commands must stay under it.
- `core`: **connection-option mapping fixes on both drivers** — `enableOfflineQueue: false` was dead on node-redis (`commandsQueueMaxLength: 0` is treated as "no limit" by the library; now mapped to the real `disableOfflineQueue` knob) and not forwarded at all on ioredis; on ioredis, `enableAutoReconnect` was wrongly wired to `enableReadyCheck` — disabling reconnects silently disabled the READY check instead while reconnects stayed on. `enableAutoReconnect: false` now maps to a null-returning `retryStrategy` and the ready check stays on.
- `leader`: **fourth adversarial-hardening pass**:
  - **the documented testing API is actually exported now** — testing.md and troubleshooting.md instruct users to import `registerLeaderServiceGetter` / `clearRegisteredLeaderGroups` from the package (stub leadership behind `@LeaderOnly`, reset the process-global registries between suites), but none of the three registry helpers reached `src/index.ts`: the published recipe failed with TS2305 and there was no sanctioned cleanup path for the cross-suite leakage the docs warn about;
  - the lapse watchdog's delay is clamped to the timer range: at the exact validation cap (`ttlMs = 2³¹−1`) the armed `remaining + 1` overflowed `setTimeout` by 1 ms and was set to 1 ms — one spurious wake plus a `TimeoutOverflowWarning` per renewal at a configuration the validator certifies as safe.
- `core`: **the default node-redis reconnect strategy no longer gives up** — it stopped after 10 retries (~2.5 min of backoff), and @redis/client treats a `false` return as PERMANENT: the client closes, no later `connect()` revives it (the base driver's stale `connected` flag short-circuits), and every election tick fails with "The client is closed" until the process restarts — a fleet-wide, unrecoverable leaderless state after any outage longer than the backoff sum. The default now retries forever with the same capped backoff (parity with ioredis); `enableAutoReconnect: false` maps to node-redis's `reconnectStrategy: false` for an intentional stay-down.
- `core`: **`commandTimeout: 0` now means "no deadline" on ioredis** — `0 ?? 5000` kept the 0, ioredis armed a 0 ms timer, and every command (including every leader acquire/renew) rejected instantly; there was no expressible value that disabled the 5 s default at all. `0` now omits the option on all three topologies.
- `core`: **the node-redis command deadline also uses the library's native per-command `timeout`** — v5 cancels a timed-out command that was never sent (removes it from the write queue), so it cannot execute server-side arbitrarily late after the local wait was abandoned; the adapter-level race remains as the envelope bound (and covers the sentinel pool-lease wait).
- `core`: `enableOfflineQueue` is now forwarded on the cluster and sentinel topologies of both drivers (previously honored only on single-node connections), and `RedisModule` **rejects two plugins with the same name** — their `Symbol.for` injection tokens collide, so Nest silently kept only the LAST instance's providers while the first plugin's options, clients, and callbacks were discarded with zero signal (e.g. two `LeaderPlugin`s "for two clusters": one set of elections simply never ran). The plugin registry also de-duplicates its lifecycle queue so a duplicate that bypasses the module cannot run hooks twice on one instance.
- `leader`: **fifth adversarial-hardening pass** — the lapse watchdog's spurious-wake path re-arms from the SAME clock read that judged the lease unlapsed: deciding with a fresh read could land 1 ms past the deadline (millisecond boundary, GC pause between two adjacent reads after a backward clock step) and silently drop the watchdog while the heartbeat was hung — leaving nobody to emit the overdue `onLost('expired')`, the exact hole the watchdog exists to cover.
- `core`: **node-redis sentinel topology was entirely broken** — the pooled client's signature is `sendCommand(isReadonly, args, options)`, but the adapter used the single-client `(args, options)` shape, so the command array landed in the ignored `isReadonly` slot and EVERY command on `type: 'sentinel'` rejected (`Cannot read properties of undefined`); leader elections never ran fleet-wide. ## [1.10.0] - 2026-08-11

### Added

## [1.9.2] - 2026-08-09

### Changed

### Fixed

### Security

## [1.8.0] - 2026-08-08

### Fixed

- `idempotency`: the default request fingerprint is now **canonical** — the body (and `query`, when included) is serialized with recursively sorted object keys, so two semantically identical bodies that differ only in key order (re-serialized by a proxy, built by a different client, generated by an LLM) no longer produce a false `422 fingerprint mismatch`. Records written by previous versions keep replaying during the upgrade window: on a mismatch the interceptor retries once with the legacy (order-sensitive) fingerprint before rejecting. The docs previously suggested `JSON.stringify(body, Object.keys(body).sort())` as a workaround — that replacer-array form is an allow-list that silently **drops nested keys** from the fingerprint; the advice is removed and warned against.
- `idempotency`: `complete()`/`fail()` now write the record fields **and** the TTL in a single atomic Lua script. Previously `HMSET` and `EXPIRE` were two separate commands: a crash between them either left the response under the leftover lock TTL (early expiry → duplicate execution) or — when the record had already expired mid-handler — re-created the key **without any TTL** (immortal record, memory leak).
- `idempotency`: the stale-lock takeover branch in the check-and-lock Lua script was dead code — the processing record's TTL equaled the staleness threshold, so by the time a lock could be considered stale the key was already gone (takeover degraded to an expire-then-race at the service level). Processing records are now retained for **2x `lockTimeout`**: once the original attempt exceeds `lockTimeout` without completing, the next request or waiter takes the lock over **atomically inside the script** (exactly one contender wins; the rest keep waiting on the new owner's record). `waitForCompletion` detects stale — not just vanished — records.

### Added

- `cache`: **stale-if-error** (RFC 5861) — serve the last known value when the loader **fails**, as a first-class availability policy independent of SWR (the freshness policy). Implements the core of [#11](https://github.com/nestjs-redisx/nestjs-redisx/issues/11) (retry backoff tracked separately). Configured as an object sibling to `swr`: `staleIfError: { enabled, defaultWindow, shouldServe }` at the plugin level, with per-call (`getOrSet`) and per-method (`@Cached`) overrides. Entries are physically retained for `window` seconds beyond their normal expiry (`keepUntil = ttl + staleTime + window`); between expiry and `keepUntil` the value is invisible to the success path — a healthy loader reloads fresh data — and is served **only** when the loader throws. `shouldServe(error)` filters which errors qualify (default: any; exclude 404/410-style "data is gone" errors so dead data is never served forever). Retries are lazy and request-driven, coalesced by stampede protection. Every stale-on-error serve logs a warning and increments `redisx_cache_stale_if_error_served_total`, so an outage cannot hide behind a green cache. The window must be a finite number — validated fail-fast at bootstrap and per call (`CacheConfigError`, new `ErrorCode.CACHE_CONFIG_INVALID`); entries of non-users keep exactly the previous TTL.
- `cache`: public **`hashKey(value)`** — hash any JSON-serializable value into a stable, CacheKey-safe 16-hex segment using the SAME frozen algorithm the `@Cached` decorator uses for auto-generated keys ([#12](https://github.com/nestjs-redisx/nestjs-redisx/issues/12)) (recursive key-sorted serialization + SHA-256 truncated to 64 bits). `{a:1,b:2}` and `{b:2,a:1}` produce the same key at every nesting level; Date/BigInt/undefined are handled. Built for the manual path — `cache.getOrSet(`calc:${hashKey(dto)}`, loader)` — so nobody has to hand-roll a key sorter. `stableStringify(value)` (the canonical serialization) is exported too, and `KeyBuilder.hashStable(obj)` adds the same hash as a fluent segment. The algorithm is a frozen contract: it will never change in place; guarded by golden-vector tests.
- `cache`: `KeyBuilder.hash()` is **deprecated** (removal in 2.0): it is key-order-sensitive (`{a:1,b:2}` ≠ `{b:2,a:1}`) and 32-bit — collisions become likely at tens of thousands of distinct objects, and a collision makes the cache serve the wrong value. Its output is intentionally unchanged so existing keys keep working; migrate to `hashStable()` / `hashKey()`.
- `idempotency`: the exception filter's response body now carries a machine-readable `code` (e.g. `IDEMPOTENCY_TIMEOUT` vs `IDEMPOTENCY_FAILED`), so clients can distinguish the 409 variants — concurrent request still in progress vs previous attempt failed — without parsing the human-readable message.
- `idempotency`: documentation now states explicitly that `defaultTtl` is the deduplication **window** (a retry after expiry re-executes; keep the durable "was this operation performed" answer in your database for money movement), that `errorPolicy: 'fail-open'` trades the idempotency guarantee for availability, and how to register the interceptor for byte-accurate response replay (idempotency outermost, response transforms deeper).

## [1.6.0] - 2026-07-24

### Added

- `@nestjs-redisx/circuit-breaker`: new package — a distributed circuit breaker (`closed` / `open` / `half-open`) backed by Redis. At its core is a pure, time-injected finite state machine (`CircuitBreakerState`) that takes an explicit `now` (no hidden `Date.now()`), so the policy is deterministic and fully unit-testable; the distributed layer replicates it 1:1 with atomic Lua scripts. - `cache`: stampede protection served **stale (pre-invalidation) values for up to 100 ms** after any load. A completed singleflight stayed in the in-process flight map (`setTimeout(delete, 100)`), so the pattern "mutation → `invalidateTags`/`delete` → immediate `getOrSet`" (SSE / TanStack Query refetch) coalesced onto the already-resolved flight: the loader was not called, the old value was returned with `stampedePrevented` incremented, and the cache was not re-populated. To make this sound, the cache write now happens **inside** the protected section (before the lock is released), which also removes a duplicate write on the SWR miss path (a plain `CacheEntry` was written and immediately overwritten by the SWR entry).
- `cache`: the package `test:integration` script pointed at a non-existent spec file and silently ran nothing; it now runs the whole `test/integration` directory sequentially.

### Changed
- `rate-limit`: the guard and the 429 exception filter now write response headers and bodies through `HttpAdapterHost` from `@nestjs/core` instead of duck-typing the Express `response`. Behaviour on Express is byte-for-byte unchanged.
- `idempotency`: the interceptor now sets status / headers via `HttpAdapterHost` and derives the request path via `httpAdapter.getRequestUrl()`. Replay behaviour on Express is unchanged.

### Removed
- `metrics`: unused `@types/express` from `devDependencies`. The package never imported from Express.

### Compatibility
- No breaking changes. Public exports (`RateLimitGuard`, `RateLimitExceptionFilter`, `IdempotencyInterceptor`, `@RateLimit`, `@Idempotent`, `@IdempotencyKey`, `StreamsPlugin`, `@StreamConsumer`, injection tokens, error classes, plugin options) are identical to `1.1.2`. The new `shutdownTimeoutMs` streams option is optional with a safe default.
